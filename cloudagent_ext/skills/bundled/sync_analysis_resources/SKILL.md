# 同步问题分析方法

**适用范围：主会话（main agent）。子代理没有 `Agent` 工具，不适用本流程。**

## 何时用

- 「数据没同步下来」「下游查不到」「两边数据不一致」
- 同步任务失败 / 延迟 / 重复消费

**不适用**：查询慢、索引缺失、执行计划问题 —— 那是 `sql-optimization` 的职责，本方法不做性能建议。

## 硬约束（先看这三条，再动手）

1. **不要读凭据或配置文件**：`db_sim.env`、`config.json`、`settings.json`、`mcp.json` 这类都不要打开。DSN 由运行时注入。**日志与代码取证一律委派** `log-diagnosis` / `code-diagnosis`；主 Agent 只在子代理不可用时自己读，并在结论里注明「未经子代理结构化取证」。
2. **日志根从环境变量取**：用 `CLOUDAGENT_LOG_ROOT` 指定的目录；没有该变量时优先 `<工作区>/logs-sim`。**不要猜目录、不要翻 `.cloudagent/`**——猜到旧夹具会让关键词全部 0 命中，从而把"日志里没有"误读成"没发生过"。
3. **已确认的计数不要重复复核**：同一张表同一 target 的 COUNT 取一次即可；要复核也只允许换一种口径（如 `get_table_stats` 交叉验证），不要重复委派同样的计数。

## 排查顺序（按序取证，不要跳步）

1. **是否被触发**：委派 `log-diagnosis` 检索调度日志；有任务表时再委派 `sql-diagnosis` 查任务记录。没有触发记录 → 先修调度，不要往下走。
2. **消费是否成功**：委派 `log-diagnosis` 查消费侧 ERROR / 异常栈 / 重试 / 位点。自己 `Read` 日志只用于确认日志根是否正确，**不作为证据来源**。
3. **业务处理是否成功**：消费成功但业务异常时，转 `code-diagnosis` 看处理逻辑。
4. **是否落库**：委派 `sql-diagnosis` 在下游按业务键计数。
5. **上游对照**：同一业务键在上游计数，与第 4 步对比。
6. **判阶段**：依据 1–5 的证据定位断点。
7. **声明缺口**：证据没拿到的命题，逐条列出并说明影响。

## 委派模板（第 1/2 步与第 4/5 步都照抄，不要把区分词放到后面）

```
① 调度侧：让 log-diagnosis 在 <log_root> 检索同步任务启动/跳过/abort 记录，给出时间与任务标识
② 消费侧：让 log-diagnosis 在 <log_root> 检索 ERROR / 重试 / offset 提交与 rebalance 记录
```

```
④ 下游/secondary 侧计数：让 sql-diagnosis 用 query_table_rows(target="secondary") 对表 <schema.table> 按 <key>=<value> 计数
⑤ 上游/primary 侧计数：让 sql-diagnosis 用 query_table_rows(target="primary") 对表 <schema.table> 按 <key>=<value> 计数
```

**必须显式指定 `subagent_type="sql-diagnosis"`**，不要依赖自动路由。

两句的目标描述**要在开头就不同**：objective 会被截断到 200 字，区分词写在后半段会导致两次委派被判定为重复而拒绝（表现为 `duplicate delegation`）。

**不要为了"复核"再委派一次同样的计数**：上下游各一次就够；需要交叉验证时用 `get_table_stats` 的规模/统计新鲜度，而不是重数一遍。

## 如何解读对照结果

| 上游 | 下游 | 说明 |
|---|---|---|
| 有 | 无 | 该表未落库：查第 1–2 步定位断点 |
| 有 | 有（数量一致） | 已同步；若业务仍异常，转第 3 步 |
| 无 | 有 | **至少说明下游写入通道未被完全阻断**；仍需排除人工补数、其它数据源、上游同步后又删除 |
| 无 | 无 | 数据本身不存在，或两侧都没走通；**不得**在没有消息队列证据时断言 MQ 故障 |

最后一行是硬约束：没有消费位点/积压/重试主题之类的直接证据时，只能写「需要 MQ 侧证据」，不能写「Kafka 故障」。

**日志检索为空时**，必须在 limitations 里写成「该日志根下未检索到 X」，并注明日志根路径；不得写成「X 未发生」。若日志根明显不对（只有别的域的服务名），先换 `CLOUDAGENT_LOG_ROOT` 再下结论。

## 缺口怎么写

每条缺口必须**具名且可核销**：

```
- 缺口：<命题>｜现状：<已尝试的取证>｜影响：<该命题为假时结论如何变化>｜补证方式：<具体动作>
```

不要写「信息不足」「无法判断」这类无法核销的表述。

## 停止条件

满足任一条即停：

- 已定位断点（第 1–3 步之一）且有对应证据；
- 上下游对照完成，且能区分「未落库 / 已同步 / 额外数据」；
- 预算用尽 —— 此时必须输出已有证据与缺口，不得编造结论。

## 与其它 Skill 的边界

- 性能问题（索引、执行计划、慢查询）→ `sql-optimization`
- 代码缺陷定位（非业务校验类）→ `code-analysis`
- 日志取证（含单服务、常规 ERROR 检索）→ 委派 `log-diagnosis`（其内部使用 log-analysis Skill）
- 代码取证（含仅需读一个文件）→ 委派 `code-diagnosis`（其内部使用 code-analysis Skill）

本方法只回答「数据为什么没到」，不回答「这条 SQL 为什么慢」。
