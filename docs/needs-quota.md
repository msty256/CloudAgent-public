# 需要额度 / 外部环境才能推进的事

> 整理日期：2026-11-03
> 目的：**离线能做的已经做完**，这份是"剩下的事分别卡在哪"。
> 前三类卡在模型额度或端点能力，第四类卡在本机环境，第五类卡在仓库外的项目。

---

## 1. 先说要花多少（这是排期前提）

单例实测（`code-007`，main 派发）：**输入 326 万 token / 350 秒**；`code-001` 是 143 万 / 124 秒。

| 要做的事 | 规模 | 预计输入 token | 优先级 |
|---|---|---|---|
| baseline 基线（阶段 0 的 L3） | 1 例 | ≈ 150–330 万 | **最高**，其余对照都以它为分母 |
| 阶段 5 收缩版对照 | 3 例 × 4 臂 × 1 轮 | ≈ 3900 万 | 高 |
| 阶段 5 原稿 | 7 例 × 5 臂 × 2 轮 | ≈ **1.1 亿** | 不做（跑不动） |
| 核查器 `overclaimed` 复核 | 2–3 例 | ≈ 500 万 | 中（只有它能判断核查器是否过严） |

**省钱的两条结构性办法**（都不影响对照有效性）：

1. 系统提示 25k 字符 × 每次调用是主要成本，压缩它是阶段 3 的活——但它的收益要在阶段 5 才看得见。
2. **换一个支持 prompt caching 的端点**：当前端点不返回缓存字段，等于全程全价。

## 2. 卡在「模型额度」

| # | 要做的事 | 为什么必须 live | 不做会怎样 |
|---|---|---|---|
| 1 | **baseline 基线数字** | 要真实模型跑一遍才有 token / cache / 委派数 | 所有"省了多少"都没分母，只能报单点绝对值 |
| 2 | **阶段 5 单变量对照**（`arm:inval` / `arm:reduce` / `arm:state`） | 机制效果必须两臂对比 | 只能宣称"机制保证"，不能宣称任何效果 |
| 3 | **核查器是否过严** | 实测触发 2 次、全判 `overclaimed`、分歧率 1.0，但**分不清是"判定松"还是"核查器严"** | 这个模块的价值无法评估；写进结论会站不住 |
| 4 | **main 派发约束的重跑验证** | P1 修复（加委派约束）只在单例上验过 | "委派数 1→5、自查 40→7"只有单例证据 |

## 3. 卡在「端点能力」（不是额度，是换端点）

| # | 要做的事 | 现状 |
|---|---|---|
| 1 | **cache 命中率不回退**（阶段 3 的 T3.6 对照） | 当前端点**不返回缓存字段**（阶段 0 实测 `cache_field` 为空），这个指标根本采不到。必须先换一个支持 prompt caching 的端点 |
| 2 | 成本单价实测 | 报价表是离线的静态估算；真实单价要按端点账单核 |

**注意**：第 3 节和第 2 节是两件事——就算给了额度，用当前端点也做不了 cache 对照。

## 4. 卡在「本机环境」（不需要模型额度）

| # | 要做的事 | 需要什么 | 做完的价值 |
|---|---|---|---|
| 1 | **补 sql 域 seed** | 一个可写的 PostgreSQL（本机或容器） | **14 题从 `runtime` 变 `static`**，正确率分母 17 → 31；sql 域首次可用 |
| 2 | 补 `sync-001` 的 orders 50000 行 | 同上（且要先定"下游表不存在"时 `query_table_rows` 该返回什么） | sync 域 4 → 5 |

最低要求已写在 [`case-audit-2026-11-01.md`](./case-audit-2026-11-01.md) §9：
seed 必须幂等；12 题分别依赖 `tenant_id`/`created_at`/`customer_id`/`amount`/`status` 的缺失
与 `idx_customers_region` 的存在；**补完必须把 `verification` 改掉并更新锁死的分布数字**
（`test_case_meta.py` 会红，这是故意的）。

**这是性价比最高的一项**：不需要模型额度，直接把可核题数翻倍。

## 6. 不卡在额度、但属于"还没做"的

这些是纯开发，随时可做，不需要额度：

| # | 项 | 说明 |
|---|---|---|
| 1 | 阶段 5 的多臂预设 | `variant` 目前只有 `gaps-on`/`gaps-off`；要做成"开关独立 + variant 只是预设"。开关本体（阶段 3/4 两个）已经就绪 |
| 2 | 开关泄漏守卫泛化 | 现在只守 `gaps-off` 的注入；每个开关都该有"声明关了 → 验证真关了" |
| 3 | "误停止率"定义 | 提案里有两种口径（语义误停 / 有效误停），还没选 |
| 4 | 结论级抽查载体 | 评分打的是字段匹配分，看不出"结论本身对不对"；需要一个能挂载人工/模型抽查的字段 |
| 5 | 阶段 6（E 经验沉淀 / F 记忆自评） | 提案都没写 |

## 7. 建议的推进顺序

```
① 补 sql seed（本机 PG，不花额度）        → 可核题 17 → 31
② 拿 baseline 基线（1 例，~300 万）        → 一切分母
③ 换支持 caching 的端点                    → 解锁 cache 对照 + 降成本
④ 阶段 5 收缩版对照（3 例 × 4 臂）         → 机制效果
⑤ 核查器复核（2–3 例）                     → 那个 1.0 分歧率到底怎么回事
```

②③④ 加起来约 4000 万 token；① 不花钱但能把分母翻倍，**所以排第一**。
