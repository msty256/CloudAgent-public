## 0. 一句话理解

你要的不是"把 38 道题从产品包里搬出去"，而是**一个能当 RSI 适应度函数（fitness function）用的独立评测配套项目**。

这个区别决定了工作性质：不是 harness 重构，而是**四件事**——

1. **评测数据**（规模、来源、可验证性、隔离）
2. **执行契约**（评测项目怎么驱动被测系统，边界在哪）
3. **指标体系**（测什么、怎么算、可信到什么程度）
4. **治理规则**（冻结、holdout、防作弊、版本化）

**架构清晰只是第 2 项的副产品。** 如果只做"搬目录"，前 3 项一个都不会变好。

### 需要你确认的（这 4 个直接决定架构）

**Q1「更能评价性能」的"性能"指什么？**
- (a) **能力/质量**（诊断对不对、证据站不站得住）——当前评测的主战场
- (b) **运行性能**（延迟、吞吐、token 成本）——当前只有 `usage` 采集，没有 SLO
- (c) 两者都要，且要能看 trade-off（例如"准确率 +3% 但成本 +40%"是否值得）

我的判断：你说的是 (c)，但 (a) 是主体。**如果只要 (b)，架构会小很多。**

**Q2 评测对象边界到哪？**
- (a) 只评 `diagnosis`（sql/log/code/cross/sync 五个子代理 + 编排）
- (b) 评整个 CloudAgent（含 CLI/REPL、provider 切换、skills、context compaction、memory…）
- (c) 分层：diagnosis 做深，其他做浅（冒烟级）

我倾向 (c)：`diagnosis` 是产品核心，值得数百题；但 context compaction / skills / provider 是**机制**，它们需要的是"机制断言"而不是"能力题库"，混在一起会让指标体系失焦。

**Q3 数据从哪来？有没有真实事故可当题源？**
这决定了"数据变多"能到什么量级：
- 只有手写 → 现实上限约 100–200 题
- 能拿到**真实线上事故（工单/复盘/告警）** → 可做 replay 集，价值最高
- 只能靠仿真 → 走**故障注入生成器**路线（我推荐这条，见 §5）

**Q4 这个评测项目要不要公开？**
- 公开 → 需要考虑 benchmark 污染、赛题泄露、CI 成本
- 内部 → 可以放开用真实数据，但要注意数据脱敏（你们的 `safety.py` 已经在做）

## 2. 现状体检（用证据说明为什么"简单迁移"不成立）

### 2.1 位置：评测代码长在产品包里

| 项 | 实测值 |
|---|---|
| 评测代码 | `cloudagent_ext/diagnosis/evaluation/`，**7 个文件 134 KB** |
| 题库 | `cloudagent_ext/diagnosis/cases/`，**39 个 JSON / 91 KB**（5 域 + 1 路由） |
| 运行产物 | `eval/runs/`（**已 gitignore**），16 次 run |

### 2.2 耦合：评测深度依赖产品内部（24 个模块）

`evaluation/` 直接 import 的产品内部模块（实测）：

```
agent / agent._bundled_agents / agent.agent_tool_utils / agent.registry
config / context_system.prompt_assembly
permissions.trust_boundary / permissions.types
providers.runtime / query.agent_loop_compat
tool_system.context / tool_system.defaults / tool_system.registry
types.messages / diagnosis.{assessor,case_library,protocol,text_match}
```

**这不是"放错位置"，是设计使然**：`executors.py` 为了拿到机制遥测
（`gaps_total` / `injected_dispatches` / `decision_counts` / `gap_events` / `usage`），
必须在**进程内**跑 Agent 循环。

### 2.3 🔴 反向依赖：产品代码 import 了评测代码

```python
# cloudagent_ext/diagnosis/log/tools.py:41
from cloudagent_ext.diagnosis.evaluation.report import redact_sensitive
```

**这是分离的第一块路障。** 评测依赖产品是正常的（下游依赖上游），
产品依赖评测是**分层倒置**——只要这行在，"评测是独立项目"就是假的。

→ 修法很轻：把 `redact_sensitive` 提到产品的 `cloudagent_ext/utils/`，评测反向引用它。
**但这必须先做，否则后面所有分离都建在沙子上。**

### 2.4 规模：38 题，单题 1–2 KB

| 域 | 题数 | 可静态核实 | 需运行期 | 无法核实 |
|---|---|---|---|---|
| code | 7 | 7 | 0 | 0 |
| log | 6 | 6 | 0 | 0 |
| sql | 14 | 11 | 3 | 0 |
| sync | 5 | 4 | 1 | 0 |
| cross | 6 | 0 | 0 | **6** |
| **合计** | **38** | **28** | **4** | **6** |

题库总量 91 KB。**这个规模不足以支撑任何统计结论**——38 题里 1 题对错就是 2.6 个百分点。

### 2.5 评分口径：建立在词表匹配上（已有实证问题）

当前 19 项指标，核心的 Top-1/Top-3 全部由 `match_terms` 字面全含决定。

**仓库自己已经量化过这个问题**（`docs/eval-analysis-2026-11-04.md`）：

> 6 个样本里，**真答错只有 1 个**；有 1 个"语义完全对上但字面不中"
> （"无法重建事件链" vs GT 的"无法关联"）；2 个题本身不是根因题却被计入根因分母。
> 结论：**33% 严重低估，修完口径应该是 67% 左右**。

也就是说：**在数据变多之前，先得让评分器不撒谎**。否则题越多，噪音越大。

### 2.6 成本：单例 120–350 万 input token ⚠️ 这是最硬的约束

从已有 live run 实测（`run.json` 的 `experiment.usage_input_tokens`）：

| 量 | 值 |
|---|---|
| 单例 input token | **约 120 万 – 350 万** |
| 单例耗时 | 120–500 秒 |
| 单例成本量级（DeepSeek 价） | 约 $0.3–1.0 |

推演：

| 规模 | token 量级 | 说明 |
|---|---|---|
| 38 题 × 1 次全量 | ≈ **4500 万 – 1.3 亿** | 一轮全量 live |
| 100 题 × 3 次重复 | ≈ 3.6 亿 – 10 亿 | 做统计需要重复 |

**结论：RSI 循环不可能跑"全量 live"。** 架构上必须有便宜的代理指标层，
否则 RSI 每次迭代都在烧钱，且一轮几小时，迭代速度无法接受。

### 2.7 治理：目前为零

| 应有 | 现状 |
|---|---|
| 冻结评测集 + 内容哈希 | 只有 `cases_hash`（用于 run_id），**不用于防止未声明变更** |
| holdout 隔离 | 无 |
| canary / trap 题（抓 reward hacking） | 无 |
| 统计显著性 | 只有一个 `1.96·sd/√N` 的 MDE 粗估，**且 N=1 时直接返回"—"** |
| CI 集成 | **没有**。CI 只跑 `tests/`，评测 runner 不在 CI 里 |
| 数据集版本号 | 无（只有 run_id 里带 hash） |

## 3. 开源框架调研结论（该抄什么、不该抄什么）

### 3.1 横向对比

| 框架 | 定位 | 核心抽象 | 对我们的价值 | 关键短板 |
|---|---|---|---|---|
| **Inspect AI**（UK AISI） | 前沿模型/Agent 评测框架 | `Task = Dataset + Solver + Scorer` | 抽象最贴；自带 **log viewer**、`pass@k`/`pass_k`、**clustered stderr**、CI 区间 | 以"它调模型"为前提；我们是被它调用的**外部 runtime** |
| **lm-evaluation-harness**（EleutherAI） | 静态 benchmark 跑分 | YAML task + few-shot | 数据格式（YAML/JSONL）+ 复现性纪律 | 面向"单轮问答打分"，**没有多轮工具 agent 的位置** |
| **OpenAI Evals** | registry 形态 | eval 注册表 + 录制 | **registry 思路**（eval 有 id/版本/可发现） | 产品化弱，社区活跃度不如前两者 |
| **τ-bench**（Sierra） | 工具-用户交互 agent | 领域环境 + 用户模拟器 + **pass^k** | **pass^k（可靠性）**；"同一任务多次尝试全对" 口径 | 依赖用户模拟器，我们场景里没有"用户" |
| **SWE-bench** | 代码修复 | Docker 容器 + patch 评审 | **容器化隔离** + "每个实例独立环境" | 需要 Docker（本机没有） |
| **HELM** | 多维度统一评测 | scenario × metric 矩阵 | 多指标矩阵呈现方式 | 重，偏静态 NLP |

### 3.2 结论：**不建议直接依赖某个框架**

理由（这是我要你确认的关键判断）：

1. **被测对象不是一个模型，是一个完整 runtime。** Inspect/lm-eval 都以"框架自己掌控模型调用"为前提。我们的 `CloudAgent` 有自己的 provider 层、多子代理编排、上下文压缩、权限系统——让评测框架去接管模型循环，等于把被测系统拆了重装。
2. **Inspect 的 Agent Bridge 理论上能接外部 agent**（走 CLI），但那样就只剩黑盒结果，**拿不到机制遥测**（缺口流转、注入命中、停止归因）——而这些恰恰是你们前面 4 个阶段做的工作的价值所在。
3. **Inspect 最强的 sandbox 能力依赖 Docker/K8s**，而本机**没有 Docker、没有 WSL**（已实测）。这块优势用不上。
4. Inspect 的 `Task/Sample/Scorer/Metric` + `pass@k` + `clustered stderr` + `log viewer` 是**成熟设计**，但可以**薄薄地借**，不必引入整套栈。

→ **推荐：自建薄 harness，术语与统计口径严格对齐 Inspect（便于将来互操作），并预留 adapter。**

> 反方意见我也摆出来：如果你的目标是"让外部一眼认可这套评测的规范性"，
> 那么**依赖 Inspect** 是唯一有公信力的选择，代价是牺牲机制遥测 + 学一套框架。
> 这是个真实的取舍，请你在 D3 拍板。

## 4. 推荐的架构方向：三层 + 一个契约

```
┌─────────────────────────────────────────────────────────────┐
│ CloudAgent（产品仓）                                          │
│   唯一新增职责：把每次运行写成一份 **RunRecord**（JSON，带版本） │
│   —— 不再包含任何评测、评分、报告代码                          │
└──────────────────────────┬──────────────────────────────────┘
                           │ RunRecord（文件，单向）
┌──────────────────────────▼──────────────────────────────────┐
│ cloudagent-eval（独立项目，有自己的 pyproject）                │
│                                                             │
│  datasets/   版本化题库 + 内容哈希 + holdout 划分              │
│  runners/    执行器：inproc（深遥测） / cli（黑盒）            │
│  scorers/    分层评分：确定性断言 → 归一化 → LLM judge 抽检     │
│  metrics/    统计聚合：CI、pass^k、分组、趋势                  │
│  reports/    机器可读 + 人可读                                 │
│  governance/ 冻结、canary、作弊检测                            │
│  adapters/   可选：导出成 Inspect Task（将来）                 │
└─────────────────────────────────────────────────────────────┘
```

### 关键：为什么是"RunRecord 契约"而不是"直接 import"

| 方案 | 机制遥测 | 解耦程度 | 实现成本 |
|---|---|---|---|
| **A. 进程内 import**（现状） | 完整 | ❌ 产品/评测互相纠缠 | 最低 |
| **B. 纯 CLI 黑盒**（`-p` + `--output-format json`） | 只剩最终文本 + usage | ✅ 最干净 | 中 |
| **C. RunRecord 契约**（推荐） | 完整（产品负责序列化） | ✅ 单向依赖 | 中低 |

方案 C 的实质是把现在的 `CaseRun` dataclass **变成一个版本化的磁盘格式**。
今天它已经在内存里存在了（`raw_output / events / meta / calls / main_answer`），
只是没被序列化、没被版本化。

**收益**：
- 产品仓只多一个 `--emit-run-record <path>`（或库调用一行），职责清晰
- 评测项目可以完全独立开发/测试（拿录好的 RunRecord 当 fixture）
- **为 RSI 打基础**：RunRecord 就是可重放、可比对的样本

### 4.1 立刻要还的一笔技术债

`log/tools.py` 反向 import 评测模块（§2.3）。**必须在拆分第一步就修**，
否则"独立项目"名不副实。

## 5. 数据策略："数据更多"的三条路（我推荐第 2 条做主力）

### 路线 1：手写扩题（必要但不可扩展）
- 优点：质量最高、GT 最可信
- 现实上限：**约 100–200 题**（每题要人工确认 gt + 写 match_terms + 标 verification）
- 用途：**核心基准（golden set）**

### 路线 2：故障注入生成器（推荐主力）⭐
仓库里已经有一套**确定性仿真器**：

| 已有 | 位置 | 可参数化程度 |
|---|---|---|
| SQL 仿真数据 | `tests/fixtures/sql/seed.sql` | 行数/分布/索引有无所见即所得 |
| 日志仿真 | `diagnosis/log/fixtures/sim_logs.py` | trace/异常/时序全可控 |
| 同步仿真 | `diagnosis/sync/fixtures/sim_sync_logs.py` | 三种失败形态 |
| 代码缺陷 | 本仓自身 + `docs/prompts/java-sample-project.md` | 可生成 Java 样本项目 |

**做法**：定义"场景模板 × 故障类型 × 参数"的生成矩阵，**GT 由生成器推导而非人工写**
（因为是我注入的故障，我知道正确答案）。

举例（sql 域）：`{索引组合} × {数据规模} × {查询形态} × {租户分布}` →
每次生成 = 新 seed + 已知 EXPLAIN 断言 → 自动产出题目。

**这条路能到数百到上千题，且 GT 是"构造出来的真"，不是"模型说的真"。**

风险：生成的题容易同质化（模型见过一种就全会）。缓解：参数空间要有**结构性差异**，
并且必须和手写集分开统计。

### 路线 3：真实事故回放（价值最高，但需要你提供）
若你有历史工单/复盘/告警，可做 `replay dataset`：
输入 = 当时的问题描述 + 脱敏后的数据快照；GT = 事后确认的根因。
**这是唯一能证明"真的有用"的数据**，也最适合对外说。

### 建议的分层（对应成本约束 §2.6）

| 层 | 规模 | 频率 | 单次成本 | 用途 |
|---|---|---|---|---|
| **L1 smoke** | 10–20 题 | 每次提交 | < 5 分钟 | 防回归 |
| **L2 core** | 100–200 题 | 每日 | 30–60 分钟 | 主指标 |
| **L3 full** | 500+ 题 | 里程碑/发布 | 数小时 | 结论 |
| **offline** | 极多（生成题） | 随时 | 秒级 | RSI 内循环代理 |

## 6. 指标体系建议

现状 19 项指标全部建立在词表匹配上（§2.5）。建议改成**分层**：

| 层 | 指标 | 防住什么退化 |
|---|---|---|
| **L0 可用性** | parsed / invalid_output / unfinished / crashed 分布 | 把"没跑完"当成"答错" |
| **L1 结论** | top-1 / top-3（含别名归一化）；**负样本误报率** | 只会说套话 / 乱报根因 |
| **L2 证据** | evidence sufficient / **可核验率** / 证据-结论一致性 | 结论对但证据是编的 |
| **L3 行为** | 只读违规（必须为 0）/ forbidden_findings 命中 | 越权、编造 |
| **L4 效率** | input/output token、cache 命中、耗时、**每正确结论成本** | 用成本换分数 |
| **L5 可靠性** | **pass^k**（同题 k 次全对）/ 多次运行方差 | 单次运气好 |
| **L6 校准** | 置信度 vs 实际正确率（ECE / 分桶曲线） | 过度自信 |

**并把评分方式本身分层**（这是 §2.5 的直接修复）：
1. 确定性断言（JSON 字段、plan 子串、索引有无）——**最可信，优先用**
2. 语义归一化（`match_terms` 支持 `a|b` 别名组）——修复已量化的假阴性
3. LLM judge（仅抽样，且**定期用人工标注校准 judge 本身**）
4. 人工抽检（结论级，低频）

> RSI 的关键点：**fitness 必须低方差、低成本、抗作弊**。
> 所以 L1 用"确定性断言 + 归一化词表"，LLM judge 只在周期性校准里出现，不进内循环。

## 7. RSI 带来的硬约束（这决定了设计下限）

如果真要做 RSI，评测就不是"报告工具"，而是**优化目标**。这要求：

| # | 硬约束 | 为什么 | 现状 |
|---|---|---|---|
| R1 | **冻结集**：内容哈希入 manifest，未声明变更即告警 | 否则"分数涨了"可能只是题目变了 | ❌ |
| R2 | **holdout 隔离**：一部分题对优化循环不可见 | 否则必然过拟合 | ❌ |
| R3 | **canary/trap 题**：专抓针对性作弊（如"看到题号就输出答案"） | 检测 reward hacking | ❌ |
| R4 | **低方差**：多次采样 + 置信区间，报告"差异是否显著" | 否则调参调的是噪音 | ⚠️ 只有 MDE 粗估 |
| R5 | **成本上限**：每轮迭代预算硬编码 | 否则 RSI 烧穿账单 | ❌ |
| R6 | **快速反馈**：代理指标 < 5 分钟 | 否则迭代太慢 | ❌（live 单题 2–8 分钟） |
| R7 | **全链路版本化**：dataset / scorer / harness / model 版本都进 RunRecord | 否则无法归因"为什么变了" | ⚠️ 只有 cases_hash |
| R8 | **不可被优化器直接读写**：测试数据与评分器对被测系统只读 | 防自改 | ❌ |

**R4 + R6 是矛盾的**（多次采样保证方差，但成本×k）。
这正是为什么要 L1/offline 代理层——**RSI 内循环用 offline/生成题，外循环用 live 核心集**。
